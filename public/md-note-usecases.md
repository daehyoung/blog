# MarkDown Note System Use Cases (Narrative Strategy)

## 1. 개요 (Philosophy)

본 시스템의 유스케이스는 액터와 시스템 간의 상호작용을 **대화식(Dialog)**으로 기술합니다. 각 단계는 액터의 행동에 대한 시스템의 반응을 능동태 현재 시점으로 묘사하며, 기술적 구현의 추적을 위해 **중단점(Interruptible Point / ID)**을 흐름 내부에 명시합니다.

*   중단점은 `{기능명 [추적ID]}` 형식의 제목으로 표기하며, 이는 시스템이 일을 잠시 멈추고 사용자의 다음 행동을 기다리거나 데이터를 안전하게 커밋하는 지점을 의미합니다.

### 역할(Role) 정의
구현 기준 두 가지뿐입니다: **USER**(인증된 일반 사용자), **ADMIN**(시스템 관리자). 별도의 MANAGER 역할은 없습니다.

### 문서 상태(Status)
문서는 `DRAFT`(초안) / `PUBLISHED`(발행) 상태를 가지며, 목록·검색은 상태로 필터링합니다. **별도의 '발행' 행위(상태 전이)는 없고, 저장 시 상태를 지정하는 것으로 발행이 이뤄집니다.** (→ §6 참조: 현재 구현은 서버측 상태 머신·기본값이 없어 클라이언트가 임의 지정)

### 접근 권한 매트릭스 (문서 단위)
문서마다 다섯 플래그를 가집니다 — `groupRead`(기본 true) · `groupWrite`(false) · `publicRead`(true) · `publicWrite`(false) · `allowComments`(true).

| 동작 | 허용 조건 |
|---|---|
| **읽기** | `ADMIN` **또는** 작성자 본인 **또는** `publicRead` **또는** (`groupRead` ∧ 작성자와 같은 부서) |
| **쓰기 / 삭제** | `ADMIN` **또는** 작성자 본인 **또는** `publicWrite` **또는** (`groupWrite` ∧ 작성자와 같은 부서) |
| **권한 플래그 변경** | `ADMIN` **또는** 작성자 본인 (만) |

## 2. [Goal 1] 지식 탐색 및 소비 (Knowledge Exploration & Consumption)

*   **액터(Role)**: 일반 사용자(USER) — 인증된 모든 사용자.
*   **최종 가치**: 액터는 조직의 지식 자산을 효과적으로 탐색하여 지능적인 업무 의사결정을 지원받는다.
*   **선행 조건**: 액터는 유효한 계정으로 인증(로그인, `UC-U-01`)을 마친 상태이다. *(로그인은 세 Goal이 공유하는 인증 전제이며, 그 상호작용 자체는 아래 기본 흐름에 명시한다.)*
*   **사후 조건**: 열람 활동이 로그에 기록되고, 액터가 작성한 댓글이 해당 문서의 대화 스레드에 반영된 상태이다.

### 기본 흐름 (Basic Flow)

#### **{로그인 [UC-U-01]}**
*   **필수 정보 (Collaboration Payload)**: 사용자 식별자(ID), 비밀번호(Password)
1. **액터는** 시스템에 접속하기 위해 자신의 자격 증명을 입력하고 인증을 요청한다.
2. **시스템은** 입력된 정보를 검증하고, 유효한 경우 접근 토큰을 발급한다. *(구현: JWT)*

#### **{문서 목록 조회 (VIEW 모드) [UC-D-01A]}**
*   **필수 정보 (Collaboration Payload)**: 카테고리 ID (선택), 상태 필터(선택), 페이징 정보
3. **시스템은** 액터의 권한에 맞는 홈 화면과 카테고리 트리 구조를 구성하여 보여준다.
4. **액터는** 특정 카테고리를 선택하거나 목록에서 지식을 탐색한다.
5. **시스템은** 위 **권한 매트릭스로 읽기 가능한 문서** 중 **`PUBLISHED` 상태**만 필터링하여 페이징 제공한다.

#### **{문서 검색 [UC-D-04]}**
*   **필수 정보 (Collaboration Payload)**: 검색 키워드 (Query String), 페이징 정보
6. **액터는** 전역 검색을 통해 제목·태그가 일치하는 문서를 찾는다.
7. **시스템은** 목록 조회와 **동일한 읽기 권한·상태 필터를 적용**하여 매칭 결과를 제공한다. *(→ §6: 현재 구현은 이 필터를 적용하지 않는 결함이 있음)*

#### **{문서 상세 조회 [UC-D-03]}**
*   **필수 정보 (Collaboration Payload)**: 문서 고유 번호 (Document ID)
8. **액터는** 확인하려는 문서를 선택한다.
9. **시스템은** 읽기 권한을 확인한 뒤, 해당 문서의 마크다운 전문과 다이어그램을 렌더링하여 출력한다.

#### **{댓글 등록 [UC-CM-01]}**
*   **필수 정보 (Collaboration Payload)**: 문서 ID (Target), 댓글 본문 (Text Content), 작성자 인증 정보
10. **액터는**(인증된 USER) 문서 내용에 대해 질의하거나 의견을 남기기 위해 댓글을 작성한다. *(대상 문서의 `allowComments`가 true일 때 허용 — §6 참조)*
11. **시스템은** 댓글을 저장하고 해당 문서의 대화 스레드에 즉시 반영한다.

> 스코프 아웃: 댓글의 **수정·삭제**는 본 스펙 범위 밖이다.

### 대안 흐름 (Alternative Flows)
*   2-a. **시스템은** 자격 증명이 올바르지 않으면 인증 실패 메시지를 보내고 다시 로그인을 유도한다.
*   9-a. **시스템은** 액터에게 해당 문서의 읽기 권한이 없으면 접근 거부(403)를 통보한다.

## 3. [Goal 2] 지식 생산 및 자산화 (Knowledge Production & Assetization)

*   **액터(Role)**: 지식 생산자 — 인증된 사용자(USER). *(문서 쓰기 권한은 위 매트릭스로 문서 단위 판정된다.)*
*   **최종 가치**: 액터는 개인이 습득한 정보를 정형화된 지식으로 문서화하여 조직 내 공유 가능한 자산으로 전환한다.
*   **선행 조건 (Context)**: 
    - 시스템에는 지식을 분류할 **카테고리가 최소 하나 이상 등록**되어 있어야 한다.
    - 액터는 **로그인**(`UC-U-01`)되어 있으며, **소속 그룹(부서)** 정보가 할당된 상태여야 한다. (그룹 단위 공유·권한 판정의 기준)
*   **사후 조건**: 문서가 지정 상태(`DRAFT`/`PUBLISHED`)로 **최초 영구 저장**되고(문서 ID 확정), 첨부파일이 문서에 연결되며, 이후 탐색·검색 대상에 포함된 상태이다.

> **저장 모델(Model B)** — 이 시스템은 편집 중에는 서버에 문서를 만들지 않는다. **문서 엔티티와 ID는 '문서 저장(UC-D-02-E)' 시점에 최초로 생성**되고, 그때 첨부파일이 함께 연결된다. (초안을 미리 서버에 만들어 ID를 받는 방식이 아니다.)

### 기본 흐름 (Basic Flow)

#### **{작업 대상 목록 조회 (EDIT 모드) [UC-D-01B]}**
*   **필수 정보 (Collaboration Payload)**: 액터 인증 정보, 카테고리 ID (선택), 상태 필터 (DRAFT 등)
1. **액터는** 자신이 작성 중인 초안이나 수정 권한이 있는 지식을 다루기 위해 편집 모드(EDIT)로 진입한다.
2. **시스템은** 액터가 **쓰기 권한(작성자/그룹/공개)을 가진 문서 목록**을 필터링하여 보여준다. 초안(`DRAFT`)이 우선 포함된다.

#### **{문서 작성 시작 [UC-D-02]}**
*   **필수 정보 (Collaboration Payload)**: 카테고리 ID (필수 선택), 액터 인증 정보
3. **액터는** 새로운 지식 기록을 위해 **카테고리 하나를 필수로 선택**하고 편집을 시작한다.
4. **시스템은** 마크다운 에디터를 활성화한다. *(이 시점에는 문서가 아직 영구 저장되지 않는다 — 저장 전까지 편집은 클라이언트 측에서 이뤄진다.)*

#### **{파일 첨부 [UC-D-05]}**
*   **필수 정보 (Collaboration Payload)**: 업로드 파일 데이터 (Binary/Blob)
5. **액터는** 본문의 근거로 보조 자료(파일)를 업로드한다.
6. **시스템은** 파일을 스토리지에 저장하고 본문 삽입용 **참조 URL**을 제공한다. 이 파일은 아직 **어떤 문서에도 속하지 않은 독립 상태(doc_id 없음)**이며, 문서 저장 시점에 연결된다.

#### **{문서 저장 [UC-D-02-E]}**
*   **필수 정보 (Collaboration Payload)**: 문서 제목 (Title), 마크다운 본문 (Markdown), 태그 목록 (Tags), 첨부파일 목록 (Attachments), 권한 플래그, 상태 (DRAFT/PUBLISHED)
7. **액터는** 제목·태그·공개 범위(권한 플래그)·상태를 지정하고 저장을 요청한다.
8. **시스템은** 이 시점에 **문서를 최초로 영구 생성(문서 ID 확정)**하고, 본문에 포함된 첨부파일들을 해당 문서에 연결하며, 전체를 **하나의 트랜잭션으로 원자적으로 커밋**한다.
9. **시스템은** 저장 결과(확정된 문서 ID·상태)를 액터에게 반환한다. *(별도의 '발행' 전이는 없으며, 상태를 `PUBLISHED`로 지정한 저장이 곧 발행이다.)*

### 대안 흐름 (Alternative Flows)
*   3-a. **시스템은** 카테고리를 선택하지 않으면 작성을 진행할 수 없음을 알리고 선택을 요구한다.
*   6-a. **시스템은** 파일 업로드가 실패하면(용량 초과·비허용 확장자·스토리지 오류) 사유를 통보하고 재시도를 유도한다.
*   7-a. **시스템은** 필수 항목(제목 등)이 누락되면 저장을 중단하고 보완을 요청한다.
*   8-a. **시스템은** 저장 중 오류가 나면 트랜잭션 전체를 롤백하여, 문서와 첨부 연결이 부분만 반영되는 일이 없게 한다.
*   8-b. (그룹 쓰기 문서) **시스템은** 동시 편집이 겹치면 충돌을 처리한다. *(→ §6: 현재는 낙관적 잠금이 없어 '최종 저장 우선'으로 동작)*

## 4. [Goal 3] 시스템 운영 및 보안 거버넌스 (System Governance)

*   **액터(Role)**: 시스템 관리자(ADMIN).
*   **최종 가치**: 관리자는 조직의 지식 생태계가 안전하고 체계적으로 유지될 수 있도록 통제권을 행사한다.
*   **선행 조건**: 시스템은 액터가 관리자(ADMIN) 권한을 가진 것을 확인한 상태이다.
*   **사후 조건**: 계정·부서·카테고리에 대한 변경이 영구 반영되고, 조직 전체에 일관된 지식 체계와 접근 권한 컨텍스트가 배포된 상태이다.

### 기본 흐름 (Basic Flow)

#### **{사용자 목록 조회 [UC-A-01A]}**
*   **필수 정보 (Collaboration Payload)**: 필터 조건 (부서 ID, 역할 등), 페이징 파라미터(Offset, Limit)
1. **액터는** 조직 내 사용자를 관리하기 위해 사용자 목록을 요청한다.
2. **시스템은** 전체 계정의 목록과 현재 상태를 집계하여 제공한다.

#### **{사용자 등록/수정 [UC-A-01B]}**
*   **필수 정보 (Collaboration Payload)**: 사용자 ID (Login ID), 비밀번호(*신규 생성 시*), 이메일, 성명, 역할(ADMIN/USER), 부서 정보 (Dept ID)
3. **액터는** 신규 계정을 생성하거나, 기존 사용자의 정보·역할·상태·소속 부서를 변경한다. *(비밀번호 변경은 별도 '관리자 재설정'으로 처리된다.)*
4. **시스템은** 입력을 검증하고 변경을 즉시 반영하며 관리 이력을 남긴다.

#### **{부서(그룹) 관리 [UC-A-02]}**
*   **필수 정보 (Collaboration Payload)**: 부서명 (Name), 상위 부서 식별자 (Parent Department ID / Nullable), (사용자 배정 시) 대상 사용자 ID·부서 ID
5. **액터는** 조직 구조를 반영하기 위해 부서를 등록·수정하며, 필요 시 상위 부서를 지정해 계층(트리)으로 구성한다.
6. **시스템은** 부서를 트리 구조로 저장해 사용자·문서의 **소속 컨텍스트(그룹 단위 접근 권한의 기준)**로 제공하고, 액터의 요청에 따라 사용자를 특정 부서에 배정하거나 배정을 해제한다.

#### **{시스템 카테고리 관리 [UC-A-03]}**
*   **필수 정보 (Collaboration Payload)**: 카테고리 이름 (Name), 부모 카테고리 식별자 (Parent ID / Nullable), 범위 (Scope: SYSTEM / USER)
7. **액터는** 전사 분류 체계를 위해 공통(SYSTEM) 카테고리를 등록·이름 변경·이동(부모 변경)·삭제한다.
8. **시스템은** 분류 트리를 갱신하고 모든 액터에게 동일한 지식 체계를 배포한다.

#### **{시스템 모니터링 [UC-A-05]}** *(설계 예정 — §6)*
*   **필수 정보 (Collaboration Payload)**: 조회 기간, 모니터링 대상 지표
9. **액터는** 시스템의 리소스 사용량과 지식 생산 지표를 확인한다.
10. **시스템은** 통계 지표를 시각화하여 대시보드에 출력한다.

#### **{시스템 자원 최적화 [UC-A-06]}** *(설계 예정 — §6)*
*   **필수 정보 (Collaboration Payload)**: 삭제 대상 파일 ID 목록 (Orphaned File IDs)
11. **액터는** 저장 공간 효율화를 위해 연결된 문서가 없는 **고립 첨부파일 목록**을 요청한다.
12. **시스템은** `doc_id`가 비어있고 생성 후 일정 시간이 지난 파일 목록을 식별해 제공한다.
13. **액터는** 불필요한 파일을 일괄 삭제 요청한다.
14. **시스템은** 삭제 직전 각 파일이 그 사이 문서에 연결되지 않았는지 재검증하고, DB 레코드와 물리 파일을 함께 제거한다.

### 대안 흐름 (Alternative Flows)
*   3-a. **시스템은** 신규 사용자의 로그인 ID가 이미 존재하면(중복) 계정 생성을 거부하고 사유를 통보한다.
*   3-b. **시스템은** 관리자가 자기 자신을 강등·비활성화하려 하면, 잠금 상태 방지를 위해 거부한다.
*   3-c. **시스템은** 소유 문서·카테고리가 있는 사용자를 삭제하려 하면, 귀속 처리(이관/익명화)를 거친 뒤에만 삭제를 허용한다.
*   5-a. **시스템은** 하위 부서나 소속 사용자가 남아 있는 부서 삭제를 무결성 위반으로 거부한다.
*   7-a. **시스템은** 하위 카테고리나 연결된 문서가 있는 카테고리 삭제를 거부한다. *(문서는 카테고리를 필수로 참조하므로 재분류가 선행되어야 한다.)*
*   11-a. **시스템은** 삭제 실행 직전 문서에 연결된 파일은 목록에서 제외한다(Race 방지).

## 5. 후행 조건 (Post-conditions)
*   모든 지식 활동은 시스템 로그에 기록되며, 데이터베이스는 액터의 행위에 따라 최종 정합성 상태를 유지한다.
*   감사 로그 대상 행위: 인증, 문서 생성·수정·삭제, 권한 플래그 변경, 사용자·부서·카테고리 변경, 파일 삭제.

## 6. 구현 간극 (설계 ↔ 현행 코드) — 역공학 메모

> 위 스펙은 **의도된 설계**다. 현행 코드는 아래 지점에서 설계와 어긋나며, 이는 곧 **수정 대상(백로그)**이다.

**보안/권한 누출**
- **검색(UC-D-04)이 무필터**: `/api/documents/search`는 읽기 권한·상태 필터를 적용하지 않아, 타인의 `DRAFT`·비공개 문서가 검색에 노출된다(목록 조회는 필터 적용).
- **문서 단건 조회(UC-D-03)가 권한 검사 생략**: `GET /api/documents/{id}`는 `findById`만 수행 — ID만 알면 비공개 문서 열람 가능.
- **댓글이 `allowComments`를 무시(UC-CM-01)**: 플래그가 false여도 댓글이 저장된다.
- **부서·카테고리 변경이 ADMIN 게이트 없음**: `/api/departments`·`/api/categories`의 변경/삭제가 `authenticated`만 요구 — 인증 사용자 누구나 가능. 트리 조회는 완전 공개.

**데이터 정합성**
- **삭제 무결성 미검증(3-c·5-a·7-a)**: 사용자·부서·카테고리 삭제가 하위/참조 검사 없이 실행되어 FK 위반 시 **친절한 4xx가 아니라 500**으로 실패한다.
- **고아 파일 청소 부재(UC-A-06)**: `doc_id=null`로 남은 첨부는 DB 행·물리 파일 모두 영구 방치된다. 청소 스케줄러·조회 쿼리가 없다. `UC-A-06`은 **미구현**.
- **문서 상태 머신 부재(UC-D-02-E)**: `status`에 서버 기본값·전이가 없어 클라이언트가 임의 문자열을 넣을 수 있다(`"PUBLISHED"`를 서버가 세팅하는 코드 없음).
- **동시 편집 보호 부재(8-b)**: 낙관적 잠금이 없어 그룹 쓰기 문서는 '최종 저장 우선'으로 덮어써진다.

**미구현(설계만 존재)**
- `UC-A-05`(모니터링)·`UC-A-06`(자원 최적화)는 백엔드에 엔드포인트가 없다.
- **시스템 공통 코드 관리 · 권한/역할 정책 관리**: 아예 없음(역할은 `ADMIN`/`USER` 고정 문자열, 권한은 코드 하드코딩). 그래서 본 스펙에도 유스케이스로 넣지 않았다.
