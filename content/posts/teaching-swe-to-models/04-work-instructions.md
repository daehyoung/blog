> 📚 시리즈 **「모델에게 SW 엔지니어링 가르치기」 4편**입니다. [3편](/blog/teaching-swe-to-models/03-workflow)에서 *단계의 뼈대*(워크플로우)를 세웠습니다. 이번엔 각 단계 **안**을 규율하는 두 번째 층 — **작업 지침서**입니다.

워크플로우로 단계를 강제해도, 모델은 *각 단계마저 평균적으로* 처리합니다. "유스케이스를 써라" 하면 기능을 나열하고, "객체 모델을 만들어라" 하면 데이터 가방(anemic model)을 만들고, "예외를 다뤄라" 하면 `try/except: pass`를 답니다. **단계를 열어 줬을 뿐, 그 안에서 무엇을·어떻게 할지를 안 박았기 때문**입니다. 지침서가 그 빈칸을 채웁니다.

## 1. 지침 = 단계를 '프롬프트'로 박제한 것

각 단계의 작업 지침은 네 요소를 담습니다([실전편 6편](/blog/ai-coding-series/06-workflow-as-agent-prompts)의 "단계=프롬프트"를 규율 관점으로 심화).

1. **입력**: 직전 단계의 산출물(예: 유스케이스 문서).
2. **작업**: 이 단계에서 *무엇을* 도출하는가.
3. **출력 형식**: 산출물 파일·구조.
4. **완료 기준**: 무엇이 충족돼야 통과인가(다음 편의 체크리스트로 연결).

그런데 이 넷만으로는 부족합니다. 평균회귀를 실제로 막는 건 그중 **작업** 항목에 박는 **허용/금지 목록**입니다.

## 2. 핵심 장치 — 허용/금지 목록

평균 경로는 대개 *"하기 쉬운 것"* 입니다. 그러니 **하지 말 것을 명시적으로 봉쇄**하는 게 핵심입니다. 긍정 지시("좋게 짜라")는 평균을 부르지만([1편](/blog/teaching-swe-to-models/01-why-teach-engineering)), **부정 제약("이건 금지")은 평균 경로를 직접 끊습니다.**

### 예시 ① — '유스케이스 작성' 지침서 (실 프로젝트 가이드에서 추출)

가장 편향이 심한 단계입니다 — 모델은 유스케이스[^usecase]를 시키면 *기능 목록*(CRUD)으로 뭉갭니다. 실제로 쓰는 지침서는 이만큼 촘촘합니다.

```text
[입력] requirements.md (시스템 경계·액터·제약)

[작업] 액터가 '최종 가치'를 얻는 시나리오를 대화식으로 기술하라.
 각 유스케이스는 표준 구조를 채운다:
  · 유스케이스명(능동형 목적) / 액터 / 최종 가치
  · 선행 조건(시작 전 컨텍스트) / 사후 조건(성공 = 바뀐 시스템 상태)
  · 기본 흐름(해피 패스) → 예외 흐름(취소·오류·재고부족 …)
  · 중단점(IP): 화면이 멈추고 데이터가 커밋되는 지점 = API·트랜잭션 경계
  · 필수 정보(Payload): 트랜잭션을 원자적으로 성공시킬 데이터 = Request DTO 필드
 ⛔ 금지
  · 기능 분해 금지 — '로그인/저장/조회'를 독립 UC로 뽑지 마라(수단이지 가치가 아님)
  · 개발 용어 금지 — 사용자가 이해하는 말로
  · 해피 패스만 금지 — 예외 흐름 없는 UC는 미완성
  · 선행/사후 조건 생략 금지(숨은 가정 = 빠진 범위)

[출력] usecase.md (UC-1, UC-2, … + 중단점별 필수 정보)

[완료 기준] 산출물은 '유스케이스 검증 체크리스트'로 통과/반려한다
           (7개 항목의 전체 체크리스트는 → 5편에서 그대로 사용)
```

> 눈여겨볼 곳 — **중단점 → API·트랜잭션 경계**, **필수 정보 → Request DTO**로 곧장 이어집니다. 상류(유스케이스)를 제대로 쓰면 하류(모델·API)가 *기계적으로 도출*되고([실전편 5편](/blog/ai-coding-series/05-verify-design-before-code)), 위 `[완료 기준]`은 그대로 [5편의 검증 게이트](/blog/teaching-swe-to-models/05-verification)가 됩니다.

### 예시 ② — '객체 모델' 단계 지침

```text
[입력] usecase.md

[작업] 유스케이스의 콜레보레이션 데이터에서 도메인 모델을 추출하라.
 ✅ 해야 할 것
  - 각 필드는 "어느 중단점에서 쓰이는가"를 추적 가능하게
  - 상태 전이는 모델 메서드로 표현 (예: to_review())
  - 교체 가능한 부분은 인터페이스(ABC)로 분리
 ⛔ 금지
  - 유스케이스에 없는 필드를 추가하지 말 것 (과잉 설계)
  - 데이터만 있고 행동이 없는 빈 모델(anemic) 금지
  - 아직 구현하지 말 것 — 모델과 인터페이스만
```

> 보이나요? 금지 목록의 각 항목은 **모델이 그 단계에서 흔히 회귀하는 평균 실패**와 정확히 짝을 이룹니다 — CRUD화, 해피패스, anemic model, 과잉추상화. *편향의 지도를 그려, 그 위에 벽을 세우는* 겁니다.

## 3. 지침은 '사람 관행'이 아니라 '모델 실측'에 맞춘다

허용/금지 목록을 채울 때 가장 흔한 함정은 — **사람의 베스트프랙티스를 그대로 베끼는 것**입니다. 대개는 통하지만, *안 통할 때가 이 시리즈의 핵심*입니다. 모델은 사람과 다르게 학습 편향이 있어([1편](/blog/teaching-swe-to-models/01-why-teach-engineering)), **사람에게 최적인 절차가 모델에겐 역효과**일 수 있거든요.

**실제 사례 — 객체 모델 설계의 '탑다운 vs 바텀업'.**

[실전편 5편](/blog/ai-coding-series/05-verify-design-before-code)은 (사람 기준) **탑다운**을 권합니다 — *클라이언트 호출부터 쓰고, 거기서 인터페이스·파라미터 객체를 도출하고, 구현은 마지막.* 사람에겐 이게 잘 맞습니다. 전체 그림을 쥐고 추상을 먼저 세울 수 있으니까요.

그런데 **같은 지침을 모델에 강제했더니 오히려 나빠졌습니다.** 인터페이스를 먼저 못 박게 하면 모델은 *과추상화하거나 엉뚱한 경계*를 그었습니다 — 아직 안 보이는 구현을 상상해 추상을 세우는 건 판단이 필요한 프런티어라, 평균으로 새는 거죠. 반대로 **바텀업 — 동작하는 구체 구현을 먼저 만들게 하고, 거기서 인터페이스·파라미터 객체를 역추출**하게 했더니 결과가 좋았습니다. 구체 코드 생성은 학습에 사례가 넘쳐 모델이 강한 지점이니까요.

| | 사람 | 모델 (실측) |
|---|---|---|
| 잘 맞는 순서 | **탑다운** (인터페이스 먼저) | **바텀업** (구체 먼저 → 역추출) |
| 이유 | 전체를 쥐고 추상화 가능 | 추상 먼저 = 과추상·엉뚱한 경계(프런티어 판단) / 구체엔 강함 |

> 그래서 이 단계의 지침은 실전편과 **일부러 다르게** 적습니다 — "구체 구현을 먼저 만들고, 거기서 인터페이스를 끌어올려라. 추상을 먼저 확정하지 마라." 단, 바텀업의 함정(파라미터 불일치·난개발)은 남으니 *구체→인터페이스 정리*를 **사람 게이트**에서 검증합니다([5편](/blog/teaching-swe-to-models/05-verification)).

교훈은 절차 하나가 아닙니다 — **지침의 내용은 '사람에게 옳은 것'이 아니라 '이 모델에서 실제로 잘 나오는 것'으로 채워야 한다**는 것입니다. 그러려면 모델을 돌려 보고 어디서 편향으로 새는지 관찰해, 지침을 *교정*해야 합니다. 지침서는 한 번 쓰고 끝이 아니라 **실측으로 갱신되는 문서**입니다.

## 4. 왜 이게 프롬프트 한 줄보다 센가

| | 형용사 지시 | 지침서(4요소 + 허용/금지) |
|---|---|---|
| 범위 | 넓고 추상적 → 평균 부름 | 이 단계로 **좁힘** → 평균 배제 |
| 실패 차단 | "좋게"는 실패를 못 짚음 | 흔한 실패를 **명시적 금지**로 봉쇄 |
| 재현성 | 매번 결과가 흔들림 | 절차 고정 → 어느 모델이든 같은 품질 |
| 자산화 | 휘발 | **문서로 남아 재사용**([실전편 6편](/blog/ai-coding-series/06-workflow-as-agent-prompts)) |

그리고 이 지침서는 **한꺼번에 다 주지 않습니다** — 유스케이스를 쓸 땐 유스케이스 지침만 올립니다([2편의 단계별 로드](/blog/teaching-swe-to-models/02-how-to-teach-big-picture)). 좁은 문맥 + 좁은 금지 목록이라야 평균이 끼어들 틈이 없습니다.

> 이 *단계 지침 + 완료 기준의 총합*이 곧 [응결된 도메인 워크플로우](/blog/llm-agents)입니다 — 모델이 아니라 **절차의 질**이 결과를 가르고, 모델·도구가 바뀌어도 지침은 그대로 쓰입니다([벤더 중립 해자](/blog/llm-agents-series/06-agent-company-moat)).

## 5. 지침서의 한계 — 지침도 '아는 실패'만 막는다

정직하게 짚습니다. 허용/금지 목록은 **우리가 이미 아는 평균 실패**만 막습니다. 처음 겪는 실패 양상은 목록에 없으니 그대로 통과합니다. 그래서 지침서만으로는 부족하고, *산출물을 실제로 검증하는* 게이트가 뒤따라야 합니다 — 다음 편입니다.

---

> 정리: 작업 지침서는 각 단계 **안**을 규율합니다. 4요소(입력·작업·출력·완료기준)에, 평균회귀를 직접 끊는 **허용/금지 목록**을 박습니다. 금지 항목은 모델이 그 단계에서 흔히 저지르는 평균 실패(CRUD화·해피패스·anemic·과잉추상화)와 짝을 이룹니다 — *편향의 지도 위에 벽을 세우는* 것. 그리고 단계별로 그 지침만 로드합니다. 남은 건, 이 지침을 실제로 지켰는지 확인하는 **검증**입니다.
