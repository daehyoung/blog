> 📚 시리즈 **「AI 코딩 실전」 3편**입니다. 앞 편은 [2편 · 토큰·컨텍스트를 가볍게 유지하는 법](/blog/ai-coding-series/02-tokens-context-keep-light).

신입 사원에게 "*우리 회사 전체 프로젝트 다 읽고 기능 추가해*"라고 하면 멘붕이 옵니다. AI 코딩 에이전트도 똑같습니다 — 500줄짜리 파일을 통째로 던지면 길을 잃습니다. **그래서 사람이 복잡한 프로젝트를 다루는 방식(모듈로 쪼개고 → 인터페이스 정하고 → 나중에 조립)을 그대로 AI에 적용하면 됩니다.**

---

## 1. 문제 — 통째로 시키면 망가진다

같은 일을 **500줄 파일 통째로** 시킬 때와 **50줄 모듈 10개로 나눠** 시킬 때, 결과가 크게 갈립니다.

- **추론 정확도**: 모듈이 작을수록 AI가 현재 작업에 *풀 어텐션*을 쏟는다. 큰 파일은 노이즈에 주의력이 분산된다.
- **토큰 가성비**: 읽어야 할 활성 파일이 작으면 질문당 토큰이 확 줄어든다(2편의 토큰 폭발 방지).
- **디버깅**: 범위가 좁으면 에러 원인을 50\~100줄 안에서 즉시 찾는다. 큰 파일은 수천 줄을 뒤진다.

> 즉 "통째로"는 정확도·비용·디버깅 셋 다 손해입니다.

---

## 2. 해결 — 분할정복 3단계

### ① 작게 쪼갠다 (모듈화)

기능을 작은 모듈로 나눠 **한 번에 하나씩** 작업합니다. AI가 다뤄야 할 `[활성 파일]`이 작아지니 집중도·토큰·테스트 용이성이 모두 좋아집니다. 모듈 단위면 작업 직후 유닛 테스트를 돌려 **잘못된 코드가 전체로 퍼지기 전에** 잡을 수 있습니다.

### ② 명확히 기록한다 (인터페이스 + 의존성)

나중에 통합할 때 고생하지 않으려면, 각 모듈 작업 시 [`current_tasks.md`](/blog/ai-coding-series/01-doc-system-for-llm-collaboration)에 두 가지를 박제하세요.

- **인터페이스 명세**: "이 모듈은 A를 받아 B를 반환한다"는 약속.
- **의존성 지도**: "이 모듈은 `Config.ts`에 의존한다" 같은 정보 → 통합 세션에서 AI가 어떤 파일을 불러올지 안 헤맨다.

### ③ 필요할 때만 부른다 (통합 워크플로우)

통합 단계에서 **모든 코드를 다 읽을 필요가 없습니다.**

1. 각 모듈의 **인터페이스(함수 시그니처·타입 정의)만** 먼저 읽힌다.
2. "전체 로직의 흐름(Flow)만 검토해줘"라고 지시한다.
3. 실제 연결부에서 **에러가 난 곳만** 상세 구현을 읽어 고친다.

> 골든 룰 한 줄: **"작게 나누고(Modularize), 명확히 기록하며(Document), 필요할 때만 호출하라(On-demand Context)."**

---

## 2.5 작업을 굴리는 법 — WBS · 커밋 · 컨텍스트

모듈로 쪼갰으면, 그걸 **실제로 어떻게 굴리느냐**가 남습니다. 핵심은 *작업 단위 = 컨텍스트 단위 = 커밋 단위*로 맞추는 것입니다.

**① 쪼갠 걸 WBS(작업 목록)로.** 모듈과 의존 순서를 **작업 분해 목록**(WBS)으로 적습니다 — 각 줄이 *하나의 작업 단위*. 하위 모듈이 먼저, 그 위에 쌓이는 게 나중. ([1편의 `wbs.md`](/blog/ai-coding-series/01-doc-system-for-llm-collaboration)가 이것.)

```markdown
- [x] 1.1 SQLite 큐 구현        (의존: 없음)
- [ ] 1.2 PollingConsumer       (의존: 1.1)
- [ ] 1.3 TranslateWorker        (의존: 1.2)
```

**② 한 항목 = 한 컨텍스트 단위.** 그 작업에 *필요한 파일만* 올려 처리합니다. 그러면 컨텍스트가 *한 작업 분량*으로 유지돼([2편의 "가볍게 유지"](/blog/ai-coding-series/02-tokens-context-keep-light)의 실천판), 게이지가 천천히 차고 드리프트가 잘 안 생깁니다. 항목 하나를 끝낼 때마다 다음 항목 전에 컨텍스트를 정리(또는 새 세션)합니다.

**③ 완료마다 커밋 + 기록.** 작업 하나가 끝나면 **세 가지를 한 번에**:
- **커밋** — 코드를 커밋한다(자연스러운 *체크포인트*이자 되돌릴 안전점).
- **WBS 체크** — 해당 항목을 `[x]`로.
- **`current_tasks.md` 갱신** — "방금 뭘 끝냈고 다음은 뭔지".

이러면 진척이 *외부에 박제*되니, **컨텍스트를 비워도(리셋해도) 손실이 0**입니다([2편 ③ 외부 메모리](/blog/ai-coding-series/02-tokens-context-keep-light)). 매 커밋이 안전한 복귀점이라, 한 작업이 어긋나도 그 단위만 버리면 됩니다.

> 정리하면 — **WBS로 잘게 나누고 → 한 단위씩 처리하며 컨텍스트를 한 작업 분량으로 유지 → 끝나면 커밋·체크·기록.** 컨텍스트가 한 작업 이상 안 쌓이니, *큰 리셋도 드리프트도 애초에 잘 안 생깁니다.* (2편의 "반응적 리셋"이 필요 없어지는, 선제적 분할의 실체입니다.)

## 3. 그래서 — 워크플로우가 모델 '체급'을 상쇄한다

여기까지 오면 큰 그림이 보입니다. 복싱으로 치면 **모델 파라미터 수 = 체급(힘)**, **워크플로우 = 전술·기술**입니다. 체급이 낮아도 전술이 좋으면 한두 체급 위 상대까지 이깁니다.

- **반복 추론**: 같은 모델이라도 "한 번에 완벽히 짜"(단발)보다 *계획 → 코드 → 자가 검토 → 수정* 워크플로우를 태우는 편이 결과가 낫다. 그래서 **작은 모델 + 반복 추론**이 **큰 모델의 단발**을 따라잡기도 한다.
- **컨텍스트 관리로 역전**: 거대 모델이라도 파일 수십 개를 한꺼번에 던지면 길을 잃는다. 작은 모델도 **정보가 작고 명확하면** 정확도가 높다.
- **도구로 메운다**: 로그 전체를 읽는 대신 `grep`·`tail`을 쓰게 하면, 모델 지능 차이를 **도구의 정확성**으로 메운다(텐서 연산보다 리눅스 명령어가 정확하다).

**단, "작은 모델 > 큰 모델"로 오해하지 마십시오.** 진짜 축은 *반복 추론 vs 단발*입니다 — **같은 반복 추론 워크플로우를 큰 모델에 태우면 더 잘합니다.** 워크플로우가 체급을 *상쇄*하는 것은 **체급 차이가 너무 크지 않을 때**(대략 '추론 반복 vs 비추론 단발' 구도)뿐이고, 격차가 크면 전술로도 못 뒤집습니다. 요지는 '*작은 모델을 쓰라*'가 아니라 '**어떤 체급이든 단발보다 반복 추론이 낫다**'는 것입니다.

> 이건 이론 시리즈 [4편 · 작은 모델 + 루프가 큰 모델을 이긴다](/blog/llm-agents-series/04-small-model-big-loop)의 실전판입니다 — *치밀한 워크플로우가 거대 모델의 무지성 추론을 이긴다.* 비용은 1/10로 줄이면서 성능은 동급 이상으로.

---

## 결론 — AI는 '숙련된 신입 사원'이다

박사급 지식은 있지만 우리 프로젝트의 맥락·판단은 신입 수준입니다. 그러니 "**이 모듈만 읽고 이 기능부터 만들어**"라고 명확한 경계를 지어주는 것이, 당신의 쿼터와 정신 건강을 지키는 가장 좋은 방법입니다. 모델을 키우는 싸움에서 **워크플로우를 영리하게 설계하는 싸움**으로 — 그게 이 시리즈의 일관된 메시지입니다.
