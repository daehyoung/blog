## 전제: 모델 자체는 해자가 아니다

에이전트 사업의 가장 중요한 출발점은 **파운데이션 모델은 해자가 아니라는 인식**입니다. 모델은 빠르게 상향 평준화되고 교체 가능합니다(model-agnostic). 따라서 해자는 모델 *안*이 아니라 **모델을 둘러싼 시스템과 그 시스템이 누적한 자산**에 있습니다. 오케스트레이션·하네스·RAG·결정론 설계가 바로 그 구성 요소죠.

---

## 10.1 기술적 해자

- **에이전트 오케스트레이션·루프 설계**: 어떤 작업을 어떤 순서로 쪼개고, 어디서 검증하고, 언제 재계획·서브에이전트를 띄울지. 수많은 실패에서 축적되는 판단이라 문서만으로는 복제 안 됨.
- **하네스·가드 계층(도메인·언어 특화)**: 인젝션·오염·권한 일탈을 모델 바깥에서 막는 제어 계층. 특히 **한국어 + 특정 도메인(법률·회계) 가드의 공백**은 글로벌 모델이 채워주지 않아 구조적 해자가 됨.
- **RAG 파이프라인 튜닝**: 청킹 전략, 재순위 임계값, 소스 라우팅 규칙처럼 **실측으로만 얻어지는 값**. 도메인 코퍼스에 맞춘 검색 품질은 베끼기 어렵다.
- **결정론 우선 설계 판단**: 무엇을 결정론적 코드에 맡기고 무엇을 LLM 최후에 둘지의 경계. 이 경계가 안정성·비용·속도를 결정.
- **온프레미스 패키징·하드웨어 최적화**: 제한된 통합 메모리에 MoE + 양자화를 얹어 실사용 성능을 뽑는 통합 노하우. 어플라이언스로 묶는 능력 자체가 진입 장벽.

## 10.2 자산적 해자

- **평가셋·골든 데이터셋(가장 강력)**: 실제 도메인 질의·정답 쌍, 회귀 테스트, 품질 기준. 품질과 개선 속도의 원천이며 외부에서 **재현 불가**. 시간이 갈수록 복리로 누적.
- **도메인 온톨로지·템플릿·프롬프트 라이브러리**: 업무 구조를 모델이 다룰 형태로 정리한 지식 자산.
- **실패·장애 사례 코퍼스**: "무엇이 어떻게 실패하는가"의 기록. 다음 개선의 연료이자 경쟁자가 못 가진 음(陰)의 데이터.
- **전환 비용·신뢰·규제 대응 실적**: 고객 워크플로우에 깊이 박히면 교체 비용↑. 프라이버시·규제 레퍼런스 자체가 영업 자산.

### 온프레미스의 역설 — 데이터 플라이휠을 다르게 설계한다

SaaS형 에이전트는 고객 데이터로 모델을 개선하는 **데이터 플라이휠**이 해자입니다. 그러나 데이터가 고객 인프라를 떠날 수 없는 온프레미스·프라이버시 도메인에선 그 플라이휠이 약합니다. 그래서 해자를 옮겨야 합니다.

- raw 고객 데이터(×) → **고객 동의하에 익명화·집계된 실패 사례와 eval(○)**
- "데이터의 양"이 아니라 **"구조화된 도메인 노하우와 판단"**이 해자다.
- 역설적으로 이쪽이 모방이 더 어렵다 — **raw 데이터는 복제 가능하지만, 누적된 판단과 구조는 복제 불가**.

## 10.3 무엇을 공개하고 무엇을 비밀로 유지할 것인가

판단은 세 질문으로 환원됩니다.

1. **알려지면 무력화되는가?** (방어 룰, 튜닝 실측값) → **비밀**
2. **알아도 따라 할 수 없는가?** (실측 eval, 누적 판단, 도메인 데이터) → 공개해도 안전
3. **공개가 더 큰 이득을 주는가?** (철학·원칙·벤치마크 → 신뢰·영업·채용) → **공개**

| 구분 | 공개해도 되는 / 유리한 것 | 비밀로 유지할 것 |
|---|---|---|
| 설계 | 아키텍처 철학·원칙(model-agnostic, deterministic-first) | 하네스·가드 룰의 구체 구현 |
| 보안 | 보장 *방식의 원칙*(온프레미스, 데이터 미유출 구조) | 인젝션 방어 룰셋·필터 규칙 |
| 품질 | 도메인 벤치마크·정확도 지표 | 평가셋·골든 데이터셋 |
| 기술 | 사용 기술의 일반 개념(RAG·재순위·하네스) | 청크 크기·재순위 임계값·라우팅 규칙 등 실측값 |
| 모델 | 가드 모델을 쓴다는 사실·접근법 | 가드 모델 가중치·학습 데이터 |
| 데이터 | (없음) | 고객 데이터·고객별 커스터마이징·실패 코퍼스 |

### 자주 묻는 항목별 판단

| 항목 | 권장 | 이유 |
|---|---|---|
| **베이스 모델 이름** | 모호하게 / 선택적 | 모델은 commodity. 다만 *저평가*를 부르므로 포지셔닝 차원에서 흐리는 경우가 많다 |
| **파라미터 / 활성 파라미터** | 모호하게 | "13B밖에?" 오해. **크기 대신 도메인 정확도로 말하는** 게 유리 |
| **추론(루프) 단계 구성** | **비밀** (접근법만 공개) | 응결된 도메인 추론 = 해자 본체. "다단계+검증 루프를 쓴다"는 공개 OK, 구체 단계·순서·검증 지점은 비밀 |
| **에이전트 개수·오케스트레이션 구조** | **비밀** | 협업 토폴로지는 설계 IP이자 공격 표면 |
| **작업–모델 매핑** | **비밀(핵심 영업비밀)** | 수많은 실험의 산물. 비용·마진이 역산되고, 단계 구성과 합치면 시스템 골격이 복원됨 |
| **하드웨어 구성**(예: Mac Studio 128GB) | 공개 가능 | 온프레미스·자체 구동 근거. 보안 비밀 아님 |
| **벤치마크 수치** | 공개 | 신뢰 자산. 단 *어떻게* 냈는지(평가셋·튜닝)는 비밀 |
| **각 단계별 프롬프트** | **비밀** | 절차의 핵심 레시피. 문구·예시·제약이 알려지면 복제 |
| **검색 파이프라인 구체값**(청크·k·임계값·가중치) | **비밀** (개념은 공개) | 실측 튜닝값 |

패턴은 일관됩니다 — **개념·접근법은 공개해도 되지만, 그것을 작동시키는 구체적 문구·로직·임계값·정책은 비밀.** 이 구현 디테일의 총합이 곧 "알아도 못 따라 하는" 해자입니다.

> **온프레미스의 역설 주의.** 어플라이언스를 고객 인프라에 *납품*하면, 작정한 고객은 박스를 뜯어 실행 중인 모델·파라미터·단계 일부를 들여다볼 수 있습니다(클라우드보다 노출 위험↑). 그래서 해자를 **"모델 이름·파라미터 숨기기"에 걸면 안 됩니다.** 진짜 비밀은 박스에 *올라가 있지 않은* 것(평가셋·설계 노하우·지속 튜닝)과, 박스에 있어도 **알아도 못 따라 하는 것**(누적된 절차 설계 역량)이어야 합니다.

### 인젝션 방어의 미묘함

프롬프트 인젝션은 입력 채널이 하나뿐인 구조상 **완전 해결이 불가능**합니다. 그래서 방어는 "원칙은 공개, 구현은 비밀"로 가릅니다.

- **공개**: 다층 방어·결정론적 필터를 쓴다는 *접근법*, 그리고 "완전 방어는 불가능하다"는 **정직한 한계 인정** — 이 정직성 자체가 신뢰 자산.
- **비밀**: 구체적 탐지 규칙과 우회 차단 패턴. 공개하면 공격자가 경계를 피해 설계하므로 곧바로 무력화.

> 요지: **모방 비용이 높은 것(누적 판단·실측·데이터)은 일부 공개해도 해자가 유지되고, 알려지면 무력화되는 것(방어 룰·튜닝값)은 끝까지 비밀로 둔다.** 공개는 신뢰·생태계·채용이라는 또 다른 자산으로 되돌아옵니다.

## 시리즈를 마치며

LLM의 발전은 "모델 하나를 더 키우는" 방향에서 **"모델을 둘러싼 시스템(도구·루프·하네스)으로 한계를 상쇄하는"** 방향으로 이동했고, 그 시스템의 이름이 **에이전트**입니다. 그리고 사업의 관점에서 **바로 그 시스템 — 오케스트레이션·하네스·도메인 자산 — 이 곧 해자**입니다. 모델은 빌려 쓰는 것이고, 빌릴 수 없는 것(누적된 판단·평가셋·도메인 노하우)이 차별점을 만듭니다.
