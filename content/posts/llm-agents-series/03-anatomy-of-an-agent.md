> 전체 그림은 원본 글 **[LLM의 발전 과정과 에이전트](/blog/llm-agents)**, 앞 편은 **[2편 · 왜 LLM은 점점 무거워지나](/blog/llm-agents-series/02-why-llm-gets-heavy)**.

지금까지의 모델은 "생각해서 답하는 것"까지였습니다. 에이전트는 여기에 **행동·반복·검증**을 더해 단일 모델의 한계를 모델 *바깥에서* 상쇄합니다. 본질은 한 문장입니다.

> **에이전트 = LLM + 도구(Tool Use) + 루프(Loop) + 검증(Verification)**

> 참고: 정의에 **검증**을 넣은 건 *규범적 선택*입니다. 현실의 많은 에이전트는 검증 없이도 돌아가지만, **"검증이 박힌 루프"라야 성능이 나오므로** 권장 구성요소로 포함합니다(이유는 [4편](/blog/llm-agents-series/04-small-model-big-loop)에서 다룰 pⁿ 복리 오류).

이제 부품을 하나씩 봅니다.

## 7.1 도구 사용 (Tool Use / Function Calling) — 정의적 특징

LLM이 텍스트만 생성하는 데서 벗어나, **외부 도구를 호출해 실제 행동을 수행**합니다.

- 검색, 코드 실행, 파일 읽기/쓰기, API 호출, DB 조회(RAG) 등.
- 이로써 **지식 컷오프와 환각**을 우회한다: 모델이 기억에 의존하지 않고 **실제 데이터를 가져와** 근거로 삼는다.
- 결정적(deterministic) 도구로 처리할 수 있는 것은 도구에 맡기고, LLM은 마지막에만 개입시키는 **"결정론 우선, LLM 최후(deterministic-first, LLM-last)"** 설계가 가능해진다.

---

## 7.2 에이전트 루프

작업을 단계로 나누어 실행하고, **목표를 달성할 때까지 반복**합니다.

1. **사용자 의도·목표 파악**
2. **계획 수립**
3. **실행** (도구 호출 포함)
4. **검토(평가)**
   - 목표 미달성 → **재계획**, 2번으로
   - 목표 달성 → 다음으로
5. **답변 작성**

- 필요하면 **서브 에이전트 루프**를 생성해 하위 작업을 위임한다.
- 각 단계마다 결과를 검증하므로 **모델 성능 편차를 루프로 상쇄**한다(모델이 한 번 틀려도 루프가 잡아낸다).

---

## 7.3 컨텍스트 관리

에이전트는 한 작업 동안 **도구 출력·검색 청크·중간 결과**가 계속 컨텍스트로 흘러듭니다. 관리하지 않으면 **가용 컨텍스트가 순식간에 폭증**해 윈도우를 채우고, 그 순간 Lost in the Middle·속도 저하·비용 급증이 한꺼번에 터집니다. 앞 세대(추론·이력)보다 **까먹는 속도가 훨씬 빠르고, 통제 안 하면 비선형적**입니다. 그래서 관리가 선택이 아니라 필수입니다.

- 컨텍스트가 너무 길어지지 않도록 **요약·압축·정리**한다.
- 각 단계에 **그 실행에 꼭 필요한 데이터만 구성**해 전달하고, 결과를 검증한다.
- 즉 "다 넣고 똑똑해지길 바라는" 방식이 아니라 **필요한 것만 정밀하게 주는** 방식.

## 7.4 하네스 (Harness)

LLM의 **권한 밖 행동을 모델 바깥에서 제어**하는 장치입니다. 세 가지 역할을 합니다.

### ① 위험 행동 필터링·제어

모델이 "하겠다"고 내놓은 행동을 그대로 실행하지 않고, 하네스가 한 번 거릅니다.

- **되돌릴 수 없는 행동 차단·승인 요구**: `rm -rf`·파일 대량 삭제, DB의 `DROP`/`DELETE`, 송금·결제, 외부 대량 메일·메시지 발송 등은 자동 실행을 막고 **사람 승인(human-in-the-loop)**을 받게 한다.
- **권한·범위 제한(샌드박스)**: 접근 가능한 디렉터리·명령·도메인을 화이트리스트로 묶고, 그 밖의 파일 시스템·네트워크 접근은 봉쇄(권한 최소화).
- **폭주·비용 한도**: 무한 루프·반복 호출을 막는 **최대 스텝 수**, 토큰·비용 상한, 타임아웃.
- **정책 위반 출력 차단**: 비밀키·자격증명·개인정보 노출, 유해 콘텐츠를 출력 단계에서 막는다.

### ② 오염 방어

외부 입출력 데이터의 **오염**을 막습니다. 오염은 성격이 다른 두 종류입니다.

- **(1) 의도치 않은 오염 — 잘못된 정보**: 악의가 없어도 외부 데이터가 틀릴 수 있다(검색 오류·낡은 문서, 신뢰도 낮은 출처, OCR·파싱 깨짐, 부정확한 도구 출력). 모델이 이를 **사실로 받아들여 근거로 삼으면** 잘못된 입력이 그대로 "근거 있어 보이는 환각"으로 이어진다. → 출처 신뢰도 평가, 교차 확인, **근거–답변 일치 검증(grounding)**, 신뢰 도메인 화이트리스트로 거른다.
- **(2) 악의적 오염 — 프롬프트 인젝션**: 외부 텍스트(웹페이지·이메일·문서·도구 출력)에 **숨겨진 지시문**을 심어 모델을 탈취하는 공격. "이전 지시를 무시하라"류 명령 가로채기, 자격증명·내부 데이터 유출 유도, **권한 도구 오용** 유발. 사용자가 직접 넣는 **직접 인젝션**보다, 외부 콘텐츠에 숨어 들어오는 **간접 인젝션**이 더 위험하다(모르는 사이 발동). → 데이터/지시 경계 분리(외부 콘텐츠는 *데이터*로만 취급), 결정론적 필터, **권한 최소화**, 출력 검사. 단, 입력 채널이 하나뿐인 구조상 **완전 차단은 원리적으로 불가능**하므로 다층 방어로 위험만 낮춘다.

### ③ 단계별 결과 검증

루프의 "검토" 단계를 모델 바깥의 결정론적 장치로 뒷받침합니다.

- **형식·스키마 검증**: 도구 호출 인자가 JSON 스키마에 맞는지 검사 → 어긋나면 재시도.
- **실행 가능성 검증**: 코드가 컴파일·테스트를 통과하는지, SQL 문법 오류는 없는지, 파일 경로가 실재하는지.
- **근거 정합성(grounding) 검증**: 답이 실제 근거에서 나왔는지, 인용·수치가 출처에 실재하는지.
- **진척 검증(루프 가드)**: 제자리걸음·반복 감지, 목표 달성 판정으로 무한 재시도를 끊는다.
- **실패 시 폴백**: 다른 도구·프롬프트·모델로 갈아타거나 best-of-N으로 복구.

---

## 7.5 에이전트의 대가

- **반복 호출** 때문에 **시간 지연**이 발생한다.
- **메모리 사용량**이 많아진다.
- 루프·도구·검증을 조율하는 **시스템 복잡도**가 올라간다.

---

## 정리

에이전트는 **모델을 키우는 대신, 모델을 둘러싼 시스템(도구·루프·검증·하네스)으로 한계를 상쇄**합니다. 도구로 환각·컷오프를 우회하고, 루프로 다단계를 쪼개고, 하네스로 위험·오염을 막고, 검증으로 모델 편차를 잡습니다.

> 💡 **거꾸로 읽으면 — 1편이 곧 "에이전트가 하는 일"의 수동 버전입니다.** 이 글에서 본 부품들을 사람이 대화에서 손으로 흉내 내면, 그게 바로 **[1편 · LLM 잘 쓰는 법 12가지](/blog/llm-agents-series/01-llm-usage-tips)**입니다. 단계로 쪼개기(=루프), 자기·교차 검증(=검증), 근거·출처 요구·붙여넣은 지시 무시(=오염 방어/하네스), 계산을 코드로(=도구 offload), 대화 줄이기·중요한 건 처음·끝에(=컨텍스트 관리)... 12팁은 사실상 **에이전트가 자동으로 하는 일을 사용자가 수동으로 재현**한 목록이죠. 그래서 1편을 읽으면, 에이전트가 내부에서 실제로 무슨 일을 하는지 *체감*하게 됩니다.
